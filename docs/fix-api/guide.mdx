## Overview

Bybit FIX API provides low-latency access to Spot trading using the **FIX 4.4** protocol over persistent TCP/TLS connections.
It is suited for institutional traders and market makers who need deterministic message ordering and minimal per-request overhead compared to REST.

:::info
FIX API currently supports **Spot** trading only.
:::

Key differences from the REST V5 API:

| | REST V5 | FIX API |
|---|---|---|
| Connection | Stateless HTTP | Persistent TCP/TLS session |
| Encoding | JSON | Tag=Value (SOH-delimited) |
| Response model | Synchronous | Asynchronous — requests and responses are decoupled |
| Sequence | None | Strict monotonic `MsgSeqNum` per session |

## Connectivity

### Endpoints

| Environment | Host | Port |
|---|---|---|
| Mainnet | `fix.bybit.com` | `9878` |
| Testnet | `fix-testnet.bybit.com` | `9878` |

All connections must use TLS. Plain TCP is not accepted.

### Message Format

FIX messages use **Tag=Value** pairs separated by the SOH character (ASCII `0x01`). In this documentation the `|` character is used in place of SOH for readability.

```
8=FIX.4.4|9=65|35=0|49=CLIENT|56=BYBIT|34=5|52=20240101-08:00:30.000|10=123|
```

Every message begins with `BeginString (8)`, `BodyLength (9)`, and `MsgType (35)`, and ends with `CheckSum (10)`.
`BodyLength` is the byte count from tag 35 through to (but not including) the `10=` delimiter.
`CheckSum` is the sum of all byte values in the message modulo 256, formatted as a zero-padded 3-digit string.

### Session Lifecycle

```
Client                              Server
  |                                   |
  |--- TCP/TLS connect -------------->|
  |--- Logon (A) -------------------->|  API key + signature
  |<-- Logon (A) --------------------|  ConnId assigned
  |                                   |
  |--- NewOrderSingle (D) ----------->|
  |<-- ExecutionReport (8) ----------|  async ACK
  |                                   |
  |--- [Heartbeat (0) every N sec] -->|
  |<-- [Heartbeat (0)] --------------|
  |                                   |
  |--- Logout (5) ------------------->|
  |<-- Logout (5) -------------------|
  |--- TCP disconnect --------------->|
```

## Authentication

Authentication is performed during session initiation via the `Logon (A)` message.

### API Key

Generate your API key at:
- **Testnet:** https://testnet.bybit.com/app/user/api-management
- **Mainnet:** https://www.bybit.com/app/user/api-management

Two key types are supported, matching the REST V5 API:
- **System-generated keys** — use HMAC-SHA256 signing
- **Self-generated (RSA) keys** — use RSA-SHA256 signing

### Signature

Compute the signature before sending `Logon (A)`:

```
payload = BapiTimestamp + Username + BapiRecvWindow
```

| Key Type | Algorithm | `RawData` encoding |
|---|---|---|
| HMAC | HMAC-SHA256 | Lowercase hex string |
| RSA | RSA-SHA256 | Base64 string |

Set `RawDataLength (95)` to the byte length of the resulting `RawData (96)` string.

:::caution
The `BapiTimestamp (30002)` in the Logon header must satisfy:

```
server_time - recv_window <= BapiTimestamp < server_time + 1000
```

Use your local NTP-synced clock. Default `BapiRecvWindow (30001)` is `5000` ms, maximum is `60000` ms.
:::

## Message Header

Every FIX message carries a standard header. Bybit extends the header with additional fields.

### Standard Header Fields

| Tag | Field | Direction | Required | Description |
|-----|-------|-----------|----------|-------------|
| 8 | BeginString | Both | Y | Always `FIX.4.4` |
| 9 | BodyLength | Both | Y | Message body length in bytes |
| 35 | MsgType | Both | Y | Message type (see [Message Types](#message-types-reference)) |
| 49 | SenderCompID | Both | Y | Set by client to any unique identifier (e.g. your API key) |
| 56 | TargetCompID | Both | Y | Client sets to `BYBIT`; server sets to the client's `SenderCompID` |
| 34 | MsgSeqNum | Both | Y | Monotonically increasing sequence number, starting from `1` |
| 52 | SendingTime | Both | Y | UTC send time in `YYYYMMDD-HH:MM:SS.sss` format |

### Bybit Extension Header Fields

**Client → Server (include in requests):**

| Tag | Field | Required | Description |
|-----|-------|----------|-------------|
| 30002 | BapiTimestamp | N | Unix timestamp in milliseconds. Required for authenticated order requests |
| 30001 | BapiRecvWindow | N | Validity window in ms (default: `5000`, max: `60000`) |
| 30004 | Referer | N | Broker identifier, equivalent to `X-Referer` in REST V5 |

**Server → Client (returned in every response):**

| Tag | Field | Description |
|-----|-------|-------------|
| 30005 | TraceId | Server-side trace identifier for support and debugging |
| 30007 | BapiLimit | Total rate limit weight for the current window |
| 30008 | BapiLimitStatus | Remaining weight in the current window |
| 30009 | BapiLimitResetTimestamp | Unix timestamp (ms) when the current rate limit window resets |

:::caution
`BapiTimestamp (30002)` and `BapiLimitResetTimestamp (30009)` are 64-bit integers. Some FIX libraries default to 32-bit INT parsing — ensure your parser uses `int64` for these fields.
:::

## Session Messages

### Logon (MsgType = A)

The client sends `Logon` to initiate a session. The server responds with its own `Logon` acknowledging the connection.

**Request fields (Client → Server):**

| Tag | Field | Required | Description |
|-----|-------|----------|-------------|
| 98 | EncryptMethod | Y | Must be `0` (None) |
| 108 | HeartBtInt | Y | Heartbeat interval in seconds |
| 553 | Username | N | Your API key |
| 95 | RawDataLength | N | Byte length of `RawData` |
| 96 | RawData | N | Signature (see [Signature](#signature)) |
| 141 | ResetSeqNumFlag | N | `Y` to reset sequence numbers on this logon |
| 25036 | ResponseMode | N | `1` = Everything (default); `2` = OnlyAcks |
| 30023 | Expires | N | API key expiry timestamp (ms), if applicable |

**Response fields (Server → Client):**

| Tag | Field | Description |
|-----|-------|-------------|
| 30003 | ConnId | Unique connection identifier assigned by the server |

**Request example:**

```
8=FIX.4.4|9=130|35=A|49=CLIENT|56=BYBIT|34=1|52=20240101-08:00:00.000|
30002=1704096000000|30001=5000|98=0|108=30|553=YOUR_API_KEY|95=64|96=<SIGNATURE>|10=xxx|
```

### Heartbeat (MsgType = 0)

Exchanged at the interval negotiated in `HeartBtInt`. If a `TestRequest` is received, the responding `Heartbeat` must echo the same `TestReqID`.

| Tag | Field | Required | Description |
|-----|-------|----------|-------------|
| 112 | TestReqID | N | Echo of the `TestReqID` from an incoming `TestRequest` |

### TestRequest (MsgType = 1)

Either side may send a `TestRequest` to verify the session is alive. The receiver must reply with a `Heartbeat` containing the same `TestReqID`.

| Tag | Field | Required | Description |
|-----|-------|----------|-------------|
| 112 | TestReqID | Y | Arbitrary string echoed back in the response `Heartbeat` |

### Reject (MsgType = 3)

Sent by the server when a message fails session-level validation (e.g. malformed header, unexpected sequence number). This is distinct from an application-level rejection.

| Tag | Field | Required | Description |
|-----|-------|----------|-------------|
| 45 | RefSeqNum | N | `MsgSeqNum` of the rejected message |
| 371 | RefTagID | N | Tag number that caused the rejection |
| 372 | RefMsgType | N | `MsgType` of the rejected message |
| 373 | SessionRejectReason | N | Numeric reason code |
| 58 | Text | N | Human-readable rejection description |

### Logout (MsgType = 5)

Initiates session termination. The receiver should respond with its own `Logout`, after which the TCP connection may be closed.

| Tag | Field | Required | Description |
|-----|-------|----------|-------------|
| 58 | Text | N | Optional reason for logout |

## Rate Limiting

FIX API uses the same rate limit pool as REST V5. Every server response includes the current window status in its header:

| Tag | Field | Description |
|-----|-------|-------------|
| 30007 | BapiLimit | Total weight limit for the current window |
| 30008 | BapiLimitStatus | Remaining weight |
| 30009 | BapiLimitResetTimestamp | Window reset time in Unix milliseconds |

When `BapiLimitStatus` reaches `0`, subsequent requests will be rejected until the window resets.

## ResponseMode

`ResponseMode (25036)` in `Logon (A)` controls which server-originated messages are pushed to the client:

| Value | Description |
|-------|-------------|
| `1` (Everything) | All messages: order ACKs, fill reports, and passive order status push updates. **Default.** |
| `2` (OnlyAcks) | Only direct responses to your requests. Passive push updates (e.g. order fills from another session) are suppressed. |

Use `OnlyAcks` when your application manages state entirely through the synchronous ACK flow and does not need background push updates.

## Message Types Reference

| MsgType | Name | Direction | Description |
|---------|------|-----------|-------------|
| `0` | Heartbeat | Both | Session keepalive |
| `1` | TestRequest | Both | Liveness probe |
| `3` | Reject | Server → Client | Session-level message rejection |
| `5` | Logout | Both | Session termination |
| `A` | Logon | Both | Session initiation and authentication |
| `D` | [NewOrderSingle](trade/create-order) | Client → Server | Place a new order |
| `F` | [OrderCancelRequest](trade/cancel-order) | Client → Server | Cancel an existing order |
| `8` | [ExecutionReport](trade/execution-report) | Server → Client | Order ACK, fill reports, and passive status updates |
| `XAR` | [AtomicReplaceRequest](trade/amend-order) | Client → Server | Amend an existing order |
| `XCA` | OrderCancelAck | Server → Client | Cancel acknowledgement |
| `XAA` | OrderAmendAck | Server → Client | Amend acknowledgement |
