## 概覽

Bybit FIX API 透過持久 TCP/TLS 連線，使用 **FIX 4.4** 協議提供現貨交易的低延遲存取。
適合需要確定性訊息排序、且相比 REST 需要更低每次請求開銷的機構交易者與做市商。

:::info
FIX API 目前僅支援**現貨（Spot）**交易。
:::

與 REST V5 API 的主要差異：

| | REST V5 | FIX API |
|---|---|---|
| 連線 | 無狀態 HTTP | 持久 TCP/TLS 連線 |
| 編碼 | JSON | Tag=Value（SOH 分隔）|
| 回應模型 | 同步 | 非同步——請求與回應解耦 |
| 序列號 | 無 | 連線內嚴格單調遞增 `MsgSeqNum` |

## 連線設定

### 連線端點

| 環境 | Host | Port |
|---|---|---|
| 正式環境 | `fix.bybit.com` | `9878` |
| 測試環境 | `fix-testnet.bybit.com` | `9878` |

所有連線必須使用 TLS，不接受純文字 TCP 連線。

### 訊息格式

FIX 訊息使用 **Tag=Value** 鍵值對，以 SOH 字元（ASCII `0x01`）分隔。本文件以 `|` 替代 SOH 以提升可讀性。

```
8=FIX.4.4|9=65|35=0|49=CLIENT|56=BYBIT|34=5|52=20240101-08:00:30.000|10=123|
```

每條訊息以 `BeginString (8)`、`BodyLength (9)`、`MsgType (35)` 開頭，以 `CheckSum (10)` 結尾。
`BodyLength` 為從 tag 35 至（不含）`10=` 分隔符的位元組計數。
`CheckSum` 為訊息所有位元組之值的總和對 256 取模，格式化為補零的 3 位數字串。

### 連線生命週期

```
Client                              Server
  |                                   |
  |--- TCP/TLS connect -------------->|
  |--- Logon (A) -------------------->|  API 金鑰 + 簽名
  |<-- Logon (A) --------------------|  ConnId 已分配
  |                                   |
  |--- NewOrderSingle (D) ----------->|
  |<-- ExecutionReport (8) ----------|  非同步確認
  |                                   |
  |--- [Heartbeat (0) every N sec] -->|
  |<-- [Heartbeat (0)] --------------|
  |                                   |
  |--- Logout (5) ------------------->|
  |<-- Logout (5) -------------------|
  |--- TCP disconnect --------------->|
```

## 身分驗證

身分驗證在連線建立時透過 `Logon (A)` 訊息完成。

### API 金鑰

請至以下位址建立您的 API 金鑰：
- **測試環境：** https://testnet.bybit.com/app/user/api-management
- **正式環境：** https://www.bybit.com/app/user/api-management

僅支援**自行產生（RSA）金鑰** — 使用 RSA-SHA256 簽名

### 簽名

:::info
FIX API 僅支援**自行產生（RSA）金鑰**進行身分驗證。請在 API 管理頁面建立金鑰時選擇「自行產生的 API 密鑰」，上傳您的 RSA 公鑰（2048 或 4096 bits），並勾選「啟用 FIX API」。
:::

在發送 `Logon (A)` 前，依照以下步驟計算簽名：

**步驟一：決定 `expires` 並組合待簽名字串**

`expires` 為此次認證的到期時間，單位為 Unix 毫秒時間戳。建議取當前時間加上有效視窗（預設 `+5000 ms`）：

```
expires   = 當前 Unix 毫秒時間戳 + 5000
plaintext = "GET/realtime" + expires
```

例如，若當前時間為 `1704096000000`：

```
expires   = 1704096005000
plaintext = "GET/realtime1704096005000"
```

**步驟二：以 RSA 私鑰簽名並 Base64 編碼**

使用 RSA-SHA256 演算法，以您的私鑰對 `plaintext` 進行簽名，並將結果進行 Base64 編碼：

```
signature = base64( RSA_SHA256_sign(privateKey, plaintext) )
```

**步驟三：填入 Logon 欄位**

| 欄位 | 值 |
|------|----|
| `Username (553)` | 您的 API Key |
| `RawData (96)` | 上一步產生的 Base64 簽名字串 |
| `RawDataLength (95)` | `RawData` 字串的位元組長度 |
| `BapiTimestamp (30002)` | 計算 `expires` 時使用的當前 Unix 毫秒時間戳（即 `expires - 5000`，**非** `expires` 本身） |

:::caution
`BapiTimestamp (30002)` 為當前時間戳（非 `expires`），伺服器將驗證其滿足：

```
server_time - recv_window <= BapiTimestamp < server_time + 1000
```

請使用本地已同步 NTP 的時鐘。`BapiRecvWindow (30001)` 預設值為 `5000` ms，最大值為 `60000` ms。
:::

## 訊息標頭

每條 FIX 訊息都包含標準標頭，Bybit 在此基礎上擴充了額外欄位。

### 標準標頭欄位

| Tag | 欄位 | 方向 | 必填 | 說明 |
|-----|-------|-----------|----------|-------------|
| 8 | BeginString | 雙向 | Y | 固定為 `FIX.4.4` |
| 9 | BodyLength | 雙向 | Y | 訊息主體長度（位元組）|
| 35 | MsgType | 雙向 | Y | 訊息類型（參見[訊息類型一覽](#訊息類型一覽)）|
| 49 | SenderCompID | 雙向 | Y | 用戶端設定為任意唯一識別碼（如您的 API 金鑰）|
| 56 | TargetCompID | 雙向 | Y | 用戶端設為 `BYBIT`；伺服器設為用戶端的 `SenderCompID` |
| 34 | MsgSeqNum | 雙向 | Y | 單調遞增序列號，從 `1` 開始 |
| 52 | SendingTime | 雙向 | Y | UTC 發送時間，格式 `YYYYMMDD-HH:MM:SS.sss` |

### Bybit 擴充標頭欄位

**用戶端 → 伺服器（請求時附帶）：**

| Tag | 欄位 | 必填 | 說明 |
|-----|-------|----------|-------------|
| 30002 | BapiTimestamp | N | Unix 毫秒時間戳，認證委託請求時必填 |
| 30001 | BapiRecvWindow | N | 請求有效視窗（ms），預設 `5000`，最大 `60000` |
| 30004 | Referer | N | 經紀商識別碼，等同 REST V5 的 `X-Referer` |

**伺服器 → 用戶端（每個回應均包含）：**

| Tag | 欄位 | 說明 |
|-----|-------|-------------|
| 30005 | TraceId | 伺服器端追蹤識別碼，用於支援與除錯 |
| 30007 | BapiLimit | 目前視窗的總頻率限制權重 |
| 30008 | BapiLimitStatus | 目前視窗的剩餘可用權重 |
| 30009 | BapiLimitResetTimestamp | 視窗重置時間（Unix 毫秒時間戳）|

:::caution
`BapiTimestamp (30002)` 與 `BapiLimitResetTimestamp (30009)` 為 64 位元整數。部分 FIX 函式庫預設以 32 位元解析 INT 欄位——請確保您的解析器對這些欄位使用 `int64`。
:::

## 連線訊息

### Logon（MsgType = A）

用戶端發送 `Logon` 以建立連線，伺服器回應自身的 `Logon` 以確認連線。

**請求欄位（用戶端 → 伺服器）：**

| Tag | 欄位 | 必填 | 說明 |
|-----|-------|----------|-------------|
| 98 | EncryptMethod | Y | 必須為 `0`（None）|
| 108 | HeartBtInt | Y | 心跳間隔（秒）|
| 553 | Username | N | 您的 API 金鑰 |
| 95 | RawDataLength | N | `RawData` 的位元組長度 |
| 96 | RawData | N | 簽名（參見[簽名](#簽名)）|
| 141 | ResetSeqNumFlag | N | `Y` 表示在此次登入時重置序列號 |
| 25036 | ResponseMode | N | `1` = Everything（預設）；`2` = OnlyAcks |
| 30023 | Expires | N | API 金鑰到期時間戳（ms，如適用）|

**回應欄位（伺服器 → 用戶端）：**

| Tag | 欄位 | 說明 |
|-----|-------|-------------|
| 30003 | ConnId | 伺服器分配的唯一連線識別碼 |

**請求範例：**

```
8=FIX.4.4|9=130|35=A|49=CLIENT|56=BYBIT|34=1|52=20240101-08:00:00.000|
30002=1704096000000|30001=5000|98=0|108=30|553=YOUR_API_KEY|95=64|96=<SIGNATURE>|10=xxx|
```

### Heartbeat（MsgType = 0）

依據 `HeartBtInt` 協商的間隔週期性交換。若收到 `TestRequest`，回應的 `Heartbeat` 必須回傳相同的 `TestReqID`。

| Tag | 欄位 | 必填 | 說明 |
|-----|-------|----------|-------------|
| 112 | TestReqID | N | 回傳收到的 `TestRequest` 中的 `TestReqID` |

### TestRequest（MsgType = 1）

任一方均可發送 `TestRequest` 以確認連線存活。接收方必須回傳含有相同 `TestReqID` 的 `Heartbeat`。

| Tag | 欄位 | 必填 | 說明 |
|-----|-------|----------|-------------|
| 112 | TestReqID | Y | 任意字串，將在回應的 `Heartbeat` 中原樣回傳 |

### Reject（MsgType = 3）

當訊息未通過連線層驗證時（如標頭格式錯誤、序列號異常），伺服器發送此訊息。與應用層拒絕不同。

| Tag | 欄位 | 必填 | 說明 |
|-----|-------|----------|-------------|
| 45 | RefSeqNum | N | 被拒絕訊息的 `MsgSeqNum` |
| 371 | RefTagID | N | 導致拒絕的 Tag 編號 |
| 372 | RefMsgType | N | 被拒絕訊息的 `MsgType` |
| 373 | SessionRejectReason | N | 數字拒絕原因代碼 |
| 58 | Text | N | 可讀的拒絕說明 |

### Logout（MsgType = 5）

發起連線終止。接收方應回應自身的 `Logout`，之後 TCP 連線可關閉。

| Tag | 欄位 | 必填 | 說明 |
|-----|-------|----------|-------------|
| 58 | Text | N | 登出原因（選填）|

## 頻率限制

FIX API 與 REST V5 共用相同的頻率限制池。每個伺服器回應的標頭均包含目前視窗狀態：

| Tag | 欄位 | 說明 |
|-----|-------|-------------|
| 30007 | BapiLimit | 目前視窗的總權重上限 |
| 30008 | BapiLimitStatus | 剩餘可用權重 |
| 30009 | BapiLimitResetTimestamp | 視窗重置時間（Unix 毫秒時間戳）|

當 `BapiLimitStatus` 降至 `0` 時，後續請求將被拒絕，直至視窗重置。

## ResponseMode

`Logon (A)` 中的 `ResponseMode (25036)` 控制伺服器主動推送至用戶端的訊息類型：

| 值 | 說明 |
|-------|-------------|
| `1`（Everything）| 所有訊息：委託確認、成交回報及被動委託狀態推播。**預設值。** |
| `2`（OnlyAcks）| 僅回傳您請求的直接回應，被動推播更新（如來自其他連線的委託成交）將被抑制。 |

當您的應用程式完全透過同步 ACK 流程管理狀態，且不需要背景推播更新時，可使用 `OnlyAcks`。

| `XAA` | OrderAmendAck | 伺服器 → 用戶端 | 修改確認 |
